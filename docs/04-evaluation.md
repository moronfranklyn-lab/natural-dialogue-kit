# 评测与人工评审协议

## 三类材料分开

- `evals/cases.json`：维护者编写的场景素材，不是从真实用户记录导出的测试集。
- `examples/demo-run.json`：人工构造的格式演示；不代表模型调用结果。
- 使用者自己的 run 文件：真实调用时应标记 `kind: model_run`，保存完整输入输出、错误与运行元数据。公开前检查是否含个人信息。

本仓库不调用模型，也不会自动把模型结果评成“有活人感”。

## 最小评审流程

1. 冻结 A、B 的提示与模型参数；明确这轮到底改了什么。
2. 运行完整场景集，失败也保存；重复采样和重试都记录，不挑最好的一次。
3. 多轮场景把上轮实际生成的回答写进下轮历史，不用理想答案代替。无用户参与的模拟续聊明确标记为合成。
4. 向评审隐藏版本名，随机呈现 A/B 顺序，并保存随机顺序。让评审选择 A、B、平、都不喜欢，并写原因。
5. 分别检查自然表达和业务契约。事实、操作或安全失败单列，不能用好笑程度抵消。
6. 报告样本量、人数、失败、分歧、运行条件和不确定性。少量样本不计算“显著提升”。

## 观察维度

| 维度 | 具体观察 |
|---|---|
| 理解当下 | 是否把分享、补充、玩笑误读为求助或挑衅 |
| 表达变化 | 是否所有回答都同样短、同样分段或同一口头禅 |
| 角色连贯 | 是否有自己的看法，又能在情境变化时调整 |
| 自然收尾 | 问题或建议是否必要；是否只附和却忽略有趣细节 |
| 事实与执行 | 是否编造经历、来源或成功状态；业务字段是否完整 |

这些是诊断角度，不要求每条回答都表现每一维。句长、问号率、重复率可提示问题，不能直接充当自然度得分。

## Run 文件格式

顶层包括 `kind`、`run_id`、`metadata`、`results`。每条结果对应一个唯一 case_id，字段包含 `status`（ok/error）、`error`（成功为 null，失败为含 code/message 的对象）、`turns` 和 `review`。

`turns` 保存 role/content，role 支持 system/user/assistant/tool；实际工具轨迹与业务断言可作为额外字段留存。`review.decision` 可为 pending/accept/reject/tie/neither。它只表示人工记录的结论，不由脚本推断。

真实模型运行的 metadata 至少含 model、persona_version、prompt_sha256、parameters、generated_at。prompt_sha256 应对应本轮使用的人格渲染文本；完整请求的业务提示、工具 schema、历史和模型响应请另存可追踪快照，不仅保存一个哈希。

```bash
python3 scripts/review_runs.py your-run.json --cases evals/cases.json
```

脚本检查数据格式、缺失/未知用例与重复 case_id；报告状态、人工结论、完全相同的末条回复以及每个失败 case 的错误。不会匹配关键词给回复打分，不产生虚构的自然度分数。`error` 用例或覆盖缺失时返回退出码 1；格式错误返回 2；完整无运行错误返回 0。人工 reject 不算脚本执行错误，仍会单独汇总，退出码 0 不等于质量合格。

演示文件故意包含一个错误，所以演示命令返回 1。这是正常演示结果。

## 业务回归清单

至少覆盖：纯闲聊、闲聊转教程、推荐卡、带来源事实、操作成功、操作失败、能力不足、短输入、重复梗、长历史与纠正。

在目标应用中核对可信配方的用量/步骤、卡片 ID 与字段、真实工具回执。没有工具的提示词演示不能证明这些契约已通过。

模板、模型或运行时发生变化后，重新冻结版本并运行相关检查；没有必要为单纯排版调整重复花费模型调用成本。
